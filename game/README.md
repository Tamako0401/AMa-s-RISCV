# game: 用 C 写的手势游戏

两个游戏 (东方式弹幕、水果忍者式) 的 C 版, 同一份游戏代码在电脑和板子上跑。规划见 [display-plan.md](../docs/display-plan.md)。

```
core/        游戏逻辑, 板上照用: 只用整数 (fixed.h)、静态数组, 不用 libc
  gfx.h        画面接口: 游戏只能"填表", 不能自己画点 (见下)
  hand.c       手的原始结果 -> 游戏区坐标 + 防抖后的手势 (One Euro 平滑, 同 play.py)
  touhou.c     东方式 (照 model/play.py 的玩法)
  fruit.c      水果忍者式
pc/          电脑后端
  app.c        两个游戏共用: SDL2 窗口、60 帧/秒的主循环、鼠标键盘、UDP 收手的结果、统计、存帧
  touhou_pc.c  东方式接到 app.c: 鼠标 / 手怎么变成游戏的输入, --bot 怎么走
  fruit_pc.c   水果忍者式接到 app.c
  gfx_mem.c    gfx.h 的电脑版: 把"填的表"存在内存里 (板上是显示寄存器)
  render.c     照这张表用 SDL 画出来 (板上是显示硬件)
  stats.c      照这张表数每行要画多少 (给硬件定预算)
  hand_udp.c   收 model/hand_send.py 发来的手 (板上是视觉模块的寄存器)
tools/       assets.py: 图案和字库 -> build/assets.c (占位图; game/assets/<名字>.png 存在就用它)
             refmodel.py: 显示硬件的参考模型 (见最后一节)
```

每一帧发生的事 (两个游戏一样):

```
摄像头 -> hand_send.py --UDP--> hand_udp.c -> hand.c (平滑、防抖) -> 游戏的输入
                                                                      |
                     xxx_step (游戏走一步: 动、判定、计分) <-----------+
                     xxx_draw (把这一帧要画的东西填进 gfx.h 的表)
                                   |
                     render.c 照表画到窗口; stats.c 照表数负载
```

板上只换掉右边: `hand_udp.c` 换成读视觉寄存器, `gfx_mem.c` + `render.c` 换成写显示硬件, `core/` 一行不改。

## 板上 (盘古 100HP, 新显示)

```
board/gfx_hw.c   gfx.h 的板上版: 精灵记在内存里, 每帧写进显示的后台精灵表再提交; 背景、文字直接写
board/pad.c      串口来的按键: 终端打字 (ama monitor) 或手柄窗口 (ama monitor --pad) 的包, 格式见 pad.h;
                 控制台串口和第二个串口 (bsp/aux_uart.h, 星闪, 手柄板的 'P' 帧) 都收, 处理方法一样
board/local_keys.h  本机按键小表: 100HP KEY1 = A (bomb / 出刀 / 确认), KEY2 = MENU, KEY3 = RESTART, KEY4 = SLOW
board/mem.c      memset / memcpy (-nostdlib 下 gcc 清大结构体要用)
build/display_assets.c   开机写进显示的调色板和图案库 (refmodel.py firmware 生成, 和参考模型同一份 256 色量化; 压缩存放, gfx_hw.c 开机解压)
sw/app/game/     主程序: 标题画面选游戏、键盘 -> 两个游戏的输入、60 帧/秒的主循环 (等显示换帧)
```

```sh
./ama fpga build -b mes2l100hp --app game   # 位流要 DISPLAY_NEW=1 (sw/app/game/app.toml 的 params); coremark 参数相同, 共用这份位流
./ama fpga program --app game
./ama run game -b mes2l100hp --pad          # 改了 C 以后: 下载并打开手柄窗口; 不加 --pad 就在终端里打字玩
./ama sim game                              # 没板子: Verilator 跑整个 SoC + 新显示, 很慢 (约 6 秒一帧), 只看画面对不对
```

键位: 标题画面上下选、j / 空格 / 回车开始; 游戏里 wasd 或方向键移动 (终端里大写 = Shift = 东方的慢速),
j / 空格 = A (东方 bomb、水果出刀), r 重开, q 回标题, 结束后 A 重开。手柄窗口里按 m 切换成鼠标 (位置 = 画面位置)。
水果用键盘: 方向键移动刀尖, A 沿最近移动的方向冲出去一刀 (5 帧 x 32 点, 够快才切得开)。
板上按键去抖后和两路串口按键取或, 不改鼠标 / 指点方式; 标题和暂停菜单的只读 `pad: usb  sle  keys` 行,
最近 PAD_STALE 帧 (0.5 秒) 收过有效帧 / 有过按键的来源亮绿, 其余灰色 (usb = 控制台串口, sle = 第二串口)。
串口每局结束打印成绩, 每 5 秒打印 CPU 最忙一帧的拍数 (一帧 83 万拍) 和显示最忙一行的拍数。

终端只发 "按下" 和自动连发, 不发 "松开", 所以终端里按住方向键会先走一小步、停约半秒再连续走; `--pad` 没有这个问题。
串口接收有 16 字节 FIFO (`rtl/perips/uart.v`), CPU 算一帧时来的几个字节不会丢。

## 跑

```sh
brew install sdl2            # 一次
make -C game && game/build/touhou      # 或 game/build/fruit
# 另开终端, 用手玩 (MediaPipe 或自己的模型, 参数同 play.py)
model/hand_send.py model/models/gesture_recognizer.task [--student model/runs/x.pt]
```

- 没开 `hand_send.py` 时用鼠标 (东方式: 左键 bomb; 水果忍者: 鼠标就是刀, 划快点); 收到手的结果自动切到手, M 切换。R 重开, F 全屏, Q 退出。
- L 难度加一级 (K 恢复), 用来造最密的画面。`--bot` 自己动、不死, 跑统计用 (东方式绕圈躲弹, 水果忍者追着最高的水果划):
  `game/build/touhou --bot --level 8 --dump frames.jsonl --shot 1800 shot.bmp` (第 1800 帧截图并退出)。
- `make -C game check-core`: core/ 单独编译一遍 (`-ffreestanding`), 确认没用到电脑上才有的东西。

## 画面接口 (gfx.h)

画面 640x360, 720p 输出时每点放大成 2x2。从下到上:

| 层 | 内容 | 游戏怎么用 |
| --- | --- | --- |
| 底色 | 一个颜色 | 侧栏的底 |
| 背景 | 8x8 图块拼的 64x64 格, 可卷动, 只在游戏区 (`gfx_clip`) 内显示 | 星空往下流 |
| 摄像头小窗 | 160x120, 视觉输入缩小后的画面 | 放在左侧栏 |
| 精灵 | 每帧重来: `gfx_begin` 清空, `gfx_sprite` 一个个追加, 后加的盖住先加的 | 自机、boss、弹、bomb |
| 整体混色 | 整个画面往一个颜色混, 16 档; 每帧设 | 切到炸弹闪白 |
| 文字 | 1280x720 原生, 8x16 一格 (160x45), 16 色; 改了才写 | 分数、残机等 |

精灵一项: 中心 x, y; 图案编号; flags (半透明 / 加法混合 / 翻转 / 旋转缩放 / 只在游戏区显示); alpha (16 档); 角度 (256 档); 缩放 (16 = 原大)。
图案是 8/16/32/64 的正方形 RGB565, 像素只有透明 / 不透明。

## 边写边定下的硬件需求

写游戏时遇到的、硬件要怎么接的问题, 记在这里, 定接口时 (display-plan.md 第 3 步) 用。

| 写游戏时遇到 | 现在的做法 | 对硬件意味着 |
| --- | --- | --- |
| 游戏要每帧重排所有对象 | 绘制表: 每帧从头追加, 顺序即先后 | 精灵表双缓冲: CPU 顺序写后台那份, 场消隐时交换; 不需要优先级字段 |
| 弹飞出游戏区会盖到侧栏 | `GFX_CLIP` 标志 + 一对左右边界 (背景也用这对) | 两个比较器, 很便宜; 比让游戏自己裁、或再加一个侧栏图层省 |
| 小窗上要标出手的位置 | 小窗放到精灵下面 | 小窗只是背景和精灵之间的一层 |
| 发光、软边缘 | 图案用黑底画, 加法混合 | 图案不需要逐像素 alpha (省一半位数); 混合只有 不透明 / 整体半透明 / 加法 三种 |
| 米弹要朝飞行方向 | 旋转 (`GFX_AFFINE`, 256 档) | 待定: 硬件旋转, 还是预先转好 16 个方向的图 (多占 16 倍图案存储, 但画起来和普通弹一样快)。参考模型比较代价后定 |
| bomb 光环 | 64x64 的图放大到约 4.75 倍、加法、渐隐 | 一个对象一行要画约 450 点 (外框按 1.5 倍算); 缩放必须有 |
| HUD 文字 | 每帧重写约 20 个字段 (定宽, 盖掉旧的) | 文字层每帧写几百个字节, CPU 负担可以忽略 |
| 坐标、速度 | Q8 定点; 角度查表 (fixed.c) | 不需要 FPU; 判定先用方框粗筛, 近了才乘 |
| 水果一直在转 (水果忍者) | 每个水果、每个半块都 `GFX_AFFINE` | 东方式里旋转只是米弹, 这里几乎所有大对象都转, 而且转得连续, 16 个方向会一顿一顿的。预先转好也存不下: 32x32 的水果 16 个方向 32 KB, 西瓜 64x64 要 128 KB。**倾向硬件旋转** |
| 切开的两半 | 同一张"左半"图, 另一半 `GFX_FLIP_X`, 再按刀的方向转 | 翻转 + 旋转一起用: 硬件里翻转可以并进旋转矩阵 (一列取负), 不另花代价 |
| 刀光 | 最近 10 帧手的位置连成线, 顺着每一段摆几笔细长的发光图 (旋转、加法、越旧越细越淡), 首尾叠起来连成线 | 比一串光点顺得多, 不用单独的刀光层 (在 1280x720 上画平滑线, 更细但要一层专门的硬件)。参考模型 `render --blade-layer` 可以比较 |
| 汁水颜色不同 | 每种颜色一套图: 8x8 发光点、16x16 果汁团 (半透明淡出)、32x32 木板上的果汁印 (留 3 秒) | 不需要给精灵"染色"的功能, 小图多存几张就行; 果汁团和果汁印让最忙的一行从约 1100 拍涨到约 1600 拍 (50 MHz 的 72%) |
| 切到炸弹闪白 | `gfx_fade`: 整个画面往一个颜色混 16 档 | 新加的: 输出前每个点三个通道各一次混合, 便宜; 也能做开场淡入、结束变暗 |
| 连击字样跟着水果 | 写在文字层, 对齐到 8x16 的格子 | 文字层够用, 不用为它做精灵字 |
| 摄像头小窗在游戏区里 (水果忍者整个画面都是游戏区) | 小窗放左上角, 水果从它上面飞过 | 和东方式一样, 小窗在精灵下面就行 |

## 量到的数

`--bot` 跑 30 秒, 最忙一行按外框算 (透明点也算, 旋转对象外框 x 1.5):

| 游戏 | 难度 | 精灵最多 | 一行最多对象 | 一行最多要画的点 |
| --- | --- | --- | --- | --- |
| 东方式 | 1 (开局) | 63 | 22 | 360 |
| 东方式 | 5 (`--level 4`) | 209 | 45 | 648 |
| 东方式 | 9 (`--level 8`, 最难测过的) | 359 | 84 | 1083 |
| 水果忍者 | 1 (开局) | 69 | 31 | 336 |
| 水果忍者 | 5 (`--level 4`) | 90 | 40 | 640 |
| 水果忍者 | 10 (`--level 9`) | 99 | 39 | 1016 |

两个游戏的压力不一样: 东方式是**对象多** (几百个小弹), 水果忍者是**对象大而且都在转** (精灵不到 100 个, 但一个西瓜转起来外框 96 点宽)。
两个的"一行最多要画的点"都在 1000 左右, 硬件预算按这个定。

720p 下一条逻辑行约 2222 拍 (50 MHz)。照 display-plan.md 的设想 (每对象准备几拍、一拍画 8 点), 最难的一行也在几百拍,
看起来够; 但这只是粗算, 要等参考模型按存下的帧 (`--dump`) 细数, 尤其是旋转对象和 bomb 光环叠在一起时。
CPU 每帧要动的弹就是精灵数 (几百个), 要在板上数周期才知道够不够 (display-plan.md "CPU 跟不跟得上")。

## 参考模型 (tools/refmodel.py)

照存下的帧算出**硬件该出的画面** (逐像素, 以后 RTL 仿真截图要和它一样) 和**每行要用几拍**。
画法的每一步 (背景取点、旋转怎么反算图案坐标、三种混合、RGB565 怎么变成 HDMI 的 RGB888) 写在文件开头, 那就是硬件的规格。

```sh
game/build/fruit --bot --level 9 --dump fruit.jsonl --shot 1800 /dev/null    # 先存帧 (touhou 同样)
game/tools/refmodel.py render fruit.jsonl -o frame.png                        # 画最忙的那帧, 1280x720
game/tools/refmodel.py cost touhou.jsonl fruit.jsonl -o cost.png              # 每行拍数; 图: 那帧 + 每行拍数和预算
```

**RTL 照它对**: `refmodel.py export` 把一帧导出成 RTL 仿真要的数据和期望画面, `./ama test tests/display` 逐点比
(见 [display.md](../docs/display.md))。`cost --rtl` 按 RTL 实际的拍数算。为了和硬件一致, `render` 默认用 256 色调色板的图案、
每行最多 128 个对象, 小窗按 RGB332 算。

**和电脑版对过**: 同一帧, 模型画的和 SDL 画的除了摄像头小窗 (存帧里没有画面, 模型用灰色代替) 以外, 相差都在舍入以内,
旋转、加法、半透明都对得上。

### 每行画得完吗 (代价模型的参数是假设, 可以改)

假设: 背景一拍 8 点 (80 拍), 每个对象准备 `--setup` 拍, 不旋转的一拍写一个 8 点格子, 旋转的一拍 `--affine` 点。
一条逻辑行 (两条 720p 物理行) 的时间: 50 MHz 时 2222 拍。场景是两个游戏 `--bot` 最难跑 30 秒存下的帧。

| 参数 | 东方式 (难度 9) 最忙一行 | 水果忍者 (难度 10) 最忙一行 |
| --- | --- | --- |
| 50 MHz, 准备 4 拍, 旋转 1 点/拍 | 628 拍 (28%) | 1088 拍 (49%) |
| 50 MHz, 准备 8 拍, 旋转 1 点/拍 | 968 (44%) | 1232 (55%) |
| 50 MHz, 准备 16 拍, 旋转 1 点/拍 | 1648 (74%) | 1528 (69%) |
| 50 MHz, 准备 8 拍, 旋转 2 点/拍 | 968 (44%) | 832 (37%) |
| 25 MHz, 准备 8 拍 | 968 (87%) | 1232 (111%, 画不完) |

由此定下:
- **显示部分 50 MHz 够**, 不用为它上 100 MHz。
- 东方式对象多, 怕**每个对象的准备时间**长: 要做到 8 拍以内 (Y 分桶, 只看和这一行相交的对象)。
- 水果忍者怕**旋转慢**: 一拍 1 点就够, 不用做成 2 点。
- 一行最多 85 个对象: 每行的对象列表留 96~128 个位置; 超了丢掉后面的 (`render --max-objects` 能看丢掉是什么样)。

### 存储装得下吗 (`refmodel.py memory`)

把每块要用的 RAM 写成 "深度 x 宽度 x 份数", 再按盘古块 RAM 的拼法算块数: 一块 DRM18K 是 18 Kb,
可以拼成 16384x1、8192x2、4096x4、2048x9、1024x18、512x36; PDS 推断 RAM 时会把深度补成 2 的幂 ([vision.md](../docs/vision.md) 实测)。
同样的算法算现有的 CPU + 小窗 + 旧显示约 123 块, 和综合报告对得上。

| | 块数 (DRM18K) | 说明 |
| --- | --- | --- |
| CPU 和已有的 | 116 | 指令 ROM 占 64 块: 64 KB 被 PDS 复制成两份 |
| 新显示 | 56 | 图案库 30、文字层 6、行缓存 8 (一拍读写 8 点要 128 位宽, 浪费在宽度上)、其余都小 |
| 还没定 (估计) | 48 | 手势 CNN 40 (激活是猜的)、ILA 8 |
| 合计 | 220 | 50K 板 134 块: 装不下; 100K 板 310 块 (未核实): 71% |

由此定下:
- **新显示只能上 100K 板**。50K 现在只剩约 18 块, 新显示自己就要 56 块。
- 图案库按占位图算是 39 KB, 补成 2 的幂以后已经占了 64 KB 的块: **正式素材可以到 64 KB 不多花块**。
- 最大的浪费是**指令 ROM 复制成两份** (多 32 块)。用一块真双口 RAM 给取指和数据各一个读口就能省下来; 这是 CPU 那边的改动。
- 行缓存 8 块只装了 2.5 KB; 紧张时可以改用 LUT 做的分布式 RAM。

### 色深怎么定 (`refmodel.py colors`)

行缓存和混合必须是 RGB565 (存调色板编号就没法做发光、半透明)。能省的只有图案库: 图案存颜色编号, 画的时候查调色板变回 RGB565 再混合。
比了三种: RGB565 (每点 16 位)、所有图案共用 256 色 (8 位)、每张图案自己 16 色 (4 位, GBA 的做法)。
占位图是几块纯色, 怎么存都一样; 所以加 `--shaded` 给它们加上球面光照 (920 种颜色), 模拟正式素材。

| | 看得出差别的点 (差 > 24) | 看着 |
| --- | --- | --- |
| 共用 256 色 | 0.1% | 和 RGB565 几乎分不出 |
| 每张 16 色 | 0.3% | 西瓜的明暗出现色带, 苹果高光变成灰绿 |

发光的图 (光环、刀光、汁水) 三种都没问题: 它们是单色渐变, 颜色本来就少。

**定下: 图案用共用的 256 色调色板 (8 位), 行缓存和混合用 RGB565。**
图案库同样的块数能放两倍的点: 64 KB 的块放 6.5 万点 (`memory --pattern-bits 8 --patterns-kb 128`: 32 块 + 调色板 4 块)。
代价是一拍画 8 点就要一拍查 8 次调色板: 调色板存 4 份 (每份真双口查 2 个), 只多 4 块。
等有了正式素材, 用它再跑一次 `colors`, 确认 256 色够。

## 声音

电脑版默认打开 SDL2 音频, `--mute` 静音; 没有声卡或 SDL 打不开设备时也可以继续玩。
`pc/audio_sdl.c` 以 48 kHz、单声道有符号 16 位逐样本模拟外设, 左右声道内容相同。
`audio_sdl.h` 的 `audio_tone / audio_noise / audio_off / audio_beep / audio_pcm_*` 与
`sw/drivers/audio.h` 同名同单位。寄存器写入和批量驱动调用都用 `SDL_LockAudioDevice` 保护,
可以用 `audio_reg_write / audio_reg_read` 直接访问相对偏移。

模型按 [audio.md](../docs/audio.md) 的顺序计算: 相位先加 FREQ, LEN 减到零时音量立即清零,
再按新相位和 LFSR 混音, 下一输出采样才播这个 mix (保留 I2S 的一帧延迟)。噪声种子为 1,
长周期反馈 bit0 XOR bit1, 短周期 bit0 XOR bit6, 幅度 VOL × 32。
CTRL.EXACT 可以读写, 电脑版仍固定 48 kHz, 不模拟 BCLK 抖动和整数分频后的实际采样率。

PCM 使用共同约定的 `0x50 CTRL / 0x54 DATA / 0x58 LEVEL / 0x5C VOL`:
2048 个有符号 8 位样本, DATA 每次低字节先入队四个, 不足四个空位则整字丢弃。
CTRL bit0 开启, [7:4] DIV (0 当 1, 复位 3); 开启后的第一帧取样, 每个样本保持 DIV 帧。
关闭 PCM 清 FIFO、当前样本及分频计数, 保留欠载累计数; 欠载时当前样本为零,
每次应取样却为空就加一次 (65535 饱和)。LEVEL 低 16 位是排队样本数, 高 16 位是欠载数。
PCM 项为样本 × VOL, 和四路合成声道相加后饱和到 [-32768,32767]。
`audio_pcm_write(s,n)` 按四个样本成组写入并返回实际数量, 尾部不足四个不写。
软件混音沿用这个PCM模型和现有硬件接口。

`core/sound.c` 是两边共用的音效表和播放器, 只用整数和静态数组:

- `sound_play(SFX_...)` 申请声道, `sound_frame()` 每个 60 Hz 游戏帧调用一次, 开始或重开时 `sound_reset()`。
- 方波在 0~2 里先找空闲声道, 满时只有更高优先级能抢占最低优先级; 相同优先级满时丢弃。
  噪声固定用声道 3, 按同样优先级规则抢占。找到同名外部音效时改用 PCM 软件混音。
- 表里每个音效一行，依次是 `wav` 名字、`volume` (0~128, 128为原音量)、
  `type` (0方波/1噪声)、优先级和最多两步合成参数。
  每步 `{起始Hz, 结束Hz, 起始音量, 结束音量, 帧数, duty, vibratoHz}`;
  频率、音量按帧线性插值, 包含两个端点, 颤音每两帧变号。噪声的 duty 是短周期开关。
  帧数为零表示没有这一步; 有效步的帧数必须大于零, 频率加减颤音应在 0~23999 Hz 内。
- 新增音效时在 `sound.h` 加枚举, 在 `effects` 加一行, 在事件发生处 `sound_play`。
  已接射击、擦弹、敌机受击、自机受击、bomb、开始/结束、水果出刀/切中/炸弹/漏掉、标题与暂停菜单。
  当前玩法没有敌机死亡和道具拾取事件, `SFX_ENEMY_EXPLODE / SFX_ITEM` 已留音色, 等对应事件再接。
- 平台只实现 `sound_hw_tone / sound_hw_noise / sound_hw_off`:
  电脑由 `pc/audio_sdl.c` 实现; 板上由 `board/sound_hw.c` 转调驱动,
  `sw/app/game/main.c` 开机先 `board_audio_init()` 接好 GameShield 功放, 主循环推进音效。

`make -C game check-audio` 不需要声卡: 手算序列检查相位、DUTY 边界、LEN、长短 LFSR、
PCM 字节顺序/保持/满队列/欠载饱和/混音限幅; 另外检查音效包络、两步切换、优先级和全表自停。
`make -C game check-core` 继续检查共用层不依赖电脑库。

## SD 素材：立绘、背景音乐与音效

将自己的 PNG 放到 `game/assets/portraits/`，WAV/OGG/MP3 音乐放到 `game/assets/bgm/`，音效放到 `game/assets/sfx/`。
工具需要 uv 和 ffmpeg；文件名去扩展名后使用23字节以内的 ASCII，每类唯一。

```sh
uv run game/tools/pack.py                         # 输出 game/build/AMA.PAK 和编号清单 AMA.json
# 没有素材也可试：仅在 build 中生成原创几何人像/合成旋律/射击音效，不覆盖用户素材
uv run game/tools/pack.py --demo --assets game/build/demo-assets
# 程序合成的一套音效 (8 个短音效) + 12.8 秒循环 BGM, 见 game/tools/gen_sound.py 开头
uv run game/tools/gen_sound.py && uv run game/tools/pack.py --assets game/build/gen-assets
make -C game check-sd                            # FAT32镜像/读取/协议/PCM填充测试
AMA_PAK=game/build/AMA.PAK game/build/touhou       # PC 播放同一份音乐/音效和量化立绘
```

将 `AMA.PAK` 复制到 FAT32 卡的根目录，新格式化空卡上先拷这一个文件通常能保持连续。
驱动会检查整条 FAT 链，碎片文件会拒绝；失败时备份后重新格式化再复制。
不支持 exFAT、子目录和热插拔；没有卡/包/素材时照常游戏。卡槽/模块接线见 [sd.md](../docs/sd.md)。
默认用 100HP 板载 MicroSD 卡槽 (J10); 外接 SPI 模块加 `-DSD_EXTERNAL`, 接线在 `sw/bsp/board_sd.h`。

立绘每张单独量化到保留的128色，缩到64×96，以三精灵两倍显示128×192；一次一张，加载同id不重写。
音乐是 signed PCM8 / 16 kHz / 单声道。音频旁可放 `名字.loop.json`，例如 `{"start":0,"end":32000}`
(样本编号，4对齐)，不提供则播放一次；编号按每类文件名排序，查 `AMA.json`。
东方式进关调用 `bgm_play(0)` / `gfx_portrait_load(0)`，前120帧画立绘，不改变玩法。

游戏接口：`gfx_portrait_load(id)` → 每帧 `gfx_portrait(x,y,alpha)`，x/y为左上角，alpha=0~16；
音乐 `bgm_play(id)` / `bgm_stop()` / 每帧 `bgm_frame()` (暂停菜单期间也调用)。
板上启动时同步挂载SD并一次性缓存音效，电脑 `media_pc_init()` 从同一 PAK 缓存。
`AMA_PAK` 可覆盖PC包路径，默认查 `game/build/AMA.PAK` 或 `build/AMA.PAK`；修改素材后重新打包并重启。
切换立绘会短暂阻塞，应放在换场景时。卡槽和包格式见 [sd.md](../docs/sd.md)。

音效按去扩展名的文件名匹配 `core/sound.c` 的 `wav` 字段。例如放入 `sfx/shot.wav` 后，
`SFX_SHOT` 使用该文件；没有加载成功就继续原合成音效。默认名字为：
`shot / graze / enemy_hit / enemy_explode / player_hit / bomb / item / start / end / slash / cut /
fruit_bomb / miss / menu_move / menu_ok`。`volume` 可设0~128，不影响回退合成参数。
工具转换成 signed PCM8 / 16 kHz / 单声道，每项截到前1秒，不循环。
音效池固定12 KiB，按PAK目录顺序加载；放不下、格式无效或读取失败会跳过并输出名字到串口/PC stderr，
之后继续加载后续文件。1秒音效本身有16000字节，会超出池；建议使用短音效，总长约0.768秒以内。

`core/mix.c` 两端共用，每帧通过 `bgm_frame()` 把音乐和最多4个RAM音效相加，饱和到[-128,127]，
送入唯一PCM FIFO；合成方波/噪声仍由硬件/SDL模型并行输出。
同名重复触发从头播放一个声部；满员时只有更高优先级能抢占最低优先级，相同/更低优先级丢弃。
FIFO保持约800样本，补水向下4对齐，因此稳定时约797~800样本；音效排队延迟上限约50 ms加一帧调度。
`bgm_stop`/切曲只替换音乐源，已排队的约50 ms混音尾巴继续播放。音乐和音效都停后再补 `MIX_QUIET_FRAMES` (5) 帧静音才关PCM：
关的时候队列里只剩静音，不必等它放空 (放空那一刻起硬件每次取样都记一次欠载，会把串口的欠载计数搅乱)。
没有音乐也能播音效；音乐读失败只停音乐，音效从RAM继续，触发不读卡。
SD读取仍是同步的，卡故障超时或立绘上传可能跨帧，仍可能造成硬件欠载。

验证：`make -C game`、`check-core`、`check-audio`、`check-sd` 和 `sw/app/game/test/input_test.c` 宿主测试。
混音测试覆盖正负饱和、水位、重播、优先级抢占、音量、尾部、音效池边界、缺失时回退合成和读卡失败。

本次 mes2l100hp 同一工具链 `-O2`：`.text` 46476 → 48520，`.data` 56 → 56，
`.bss` 27568 → 41696 字节 (最终大小以构建产物为准)。ROM为 `.text+.data = 48576 / 63488` 字节，增加2044字节，余14912字节；
RAM静态占用41752字节，余23784字节，预留开机解压4 KiB栈后仍余19688字节。
不改为 `-Os`；旧测量中它会让游戏主循环慢约3倍。

CPU预算估计：当前RV32IM `-O2` 反汇编每个活跃音效声部每样本约17条指令，乘法两拍，
每样本另有约12条循环/饱和指令和约3条清零指令。
4声部、每帧267样本约2.2万条指令；按访存/分支停顿保守估计3~8万拍/帧
(50 MHz下约0.6~1.6 ms，约占一帧4~10%)，首次补800样本约为3倍。
这是静态估算，不包含SD/SPI等待，未上板测量；实际看串口每5秒一行的 `cpu max` 和 `pcm underrun +N`
(正常一直 +0；断粮一帧约 +267)。不带SD卡单独测PCM声道用 `ama run pcm_test` (见 [audio.md](../docs/audio.md))。
