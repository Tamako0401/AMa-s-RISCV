# game: 用 C 写的手势游戏

两个游戏 (东方式弹幕、水果忍者式) 的 C 版, 同一份游戏代码在电脑和板子上跑。规划见 [display-plan.md](../docs/display-plan.md)。
现在有东方式 (照 [model/play.py](../model/play.py) 的玩法), 水果忍者式还没写。

```
core/    游戏逻辑, 板上照用: 只用整数 (fixed.h)、静态数组, 不用 libc
  gfx.h      画面接口: 游戏只能"填表", 不能自己画点 (见下)
  hand.c     手的原始结果 -> 游戏区坐标 + 防抖后的手势 (One Euro 平滑, 同 play.py)
  touhou.c   东方式
pc/      电脑后端: SDL2 窗口、鼠标、UDP 收手的结果、统计每行负载、存帧
tools/   assets.py: 图案和字库 -> build/assets.c (占位图; game/assets/<名字>.png 存在就用它)
```

## 跑

```sh
brew install sdl2            # 一次
make -C game && game/build/touhou
# 另开终端, 用手玩 (MediaPipe 或自己的模型, 参数同 play.py)
model/hand_send.py model/models/gesture_recognizer.task [--student model/runs/x.pt]
```

- 没开 `hand_send.py` 时用鼠标 (左键 bomb); 收到手的结果自动切到手, M 切换。R 重开, F 全屏, Q 退出。
- L 难度加一级 (K 恢复), 用来造最密的画面。`--bot` 自机自己绕圈、不死, 跑统计用:
  `game/build/touhou --bot --level 8 --dump frames.jsonl --shot 1800 shot.bmp` (第 1800 帧截图并退出)。
- `make -C game check-core`: core/ 单独编译一遍 (`-ffreestanding`), 确认没用到电脑上才有的东西。

## 画面接口 (gfx.h)

画面 640x360, 720p 输出时每点放大成 2x2。从下到上:

| 层 | 内容 | 游戏怎么用 |
| --- | --- | --- |
| 底色 | 一个颜色 | 侧栏的底 |
| 背景 | 8x8 图块拼的 64x64 格, 可卷动, 只在游戏区 (`gfx_clip`) 内显示 | 星空往下流 |
| 摄像头小窗 | 160x120, 视觉输入缩小后的画面 | 放在左侧栏 |
| 精灵 | 每帧重来: `gfx_begin` 清空, `gfx_sprite` 一个个追加, 后加的盖住先加的 | 自机、boss、弹、bomb |
| 文字 | 1280x720 原生, 8x16 一格 (160x45), 16 色; 改了才写 | 分数、残机等 |

精灵一项: 中心 x, y; 图案编号; flags (半透明 / 加法混合 / 翻转 / 旋转缩放 / 只在游戏区显示); alpha (16 档); 角度 (256 档); 缩放 (16 = 原大)。
图案是 8/16/32/64 的正方形 RGB565, 像素只有透明 / 不透明。

## 边写边定下的硬件需求

写游戏时遇到的、硬件要怎么接的问题, 记在这里, 定接口时 (display-plan.md 第 3 步) 用。

| 写游戏时遇到 | 现在的做法 | 对硬件意味着 |
| --- | --- | --- |
| 游戏要每帧重排所有对象 | 绘制表: 每帧从头追加, 顺序即先后 | 精灵表双缓冲: CPU 顺序写后台那份, 场消隐时交换; 不需要优先级字段 |
| 弹飞出游戏区会盖到侧栏 | `GFX_CLIP` 标志 + 一对左右边界 (背景也用这对) | 两个比较器, 很便宜; 比让游戏自己裁、或再加一个侧栏图层省 |
| 小窗上要标出手的位置 | 小窗放到精灵下面 | 小窗只是背景和精灵之间的一层 |
| 发光、软边缘 | 图案用黑底画, 加法混合 | 图案不需要逐像素 alpha (省一半位数); 混合只有 不透明 / 整体半透明 / 加法 三种 |
| 米弹要朝飞行方向 | 旋转 (`GFX_AFFINE`, 256 档) | 待定: 硬件旋转, 还是预先转好 16 个方向的图 (多占 16 倍图案存储, 但画起来和普通弹一样快)。参考模型比较代价后定 |
| bomb 光环 | 64x64 的图放大到约 4.75 倍、加法、渐隐 | 一个对象一行要画约 450 点 (外框按 1.5 倍算); 缩放必须有 |
| HUD 文字 | 每帧重写约 20 个字段 (定宽, 盖掉旧的) | 文字层每帧写几百个字节, CPU 负担可以忽略 |
| 坐标、速度 | Q8 定点; 角度查表 (fixed.c) | 不需要 FPU; 判定先用方框粗筛, 近了才乘 |

## 量到的数

`--bot` 跑 30 秒, 最忙一行按外框算 (透明点也算, 旋转对象外框 x 1.5):

| 难度 | 精灵最多 | 一行最多对象 | 一行最多要画的点 |
| --- | --- | --- | --- |
| 1 (开局) | 63 | 22 | 360 |
| 5 (`--level 4`) | 209 | 45 | 648 |
| 9 (`--level 8`, 最难测过的) | 359 | 84 | 1083 |

720p 下一条逻辑行约 2222 拍 (50 MHz)。照 display-plan.md 的设想 (每对象准备几拍、一拍画 8 点), 最难的一行也在几百拍,
看起来够; 但这只是粗算, 要等参考模型按存下的帧 (`--dump`) 细数, 尤其是旋转对象和 bomb 光环叠在一起时。
CPU 每帧要动的弹就是精灵数 (几百个), 要在板上数周期才知道够不够 (display-plan.md "CPU 跟不跟得上")。
