# SD 卡素材 (只读 SPI / FAT32)

ROM 留给代码、基础图案和字库。立绘、PCM 音乐和音效从 SD 根目录 `AMA.PAK` 读。
无卡、初始化失败、找不到包/素材时游戏继续运行。没有写卡、热插拔或运行中重新挂载。
不改 RTL; 音乐和外部音效由CPU软件混音后共用现有PCM声道。

## 板载槽与外接模块

**100HP 扩展底板有板载 MicroSD 槽 J10，支持 SPI，电压 3.3 V。**
依据配套《教程1_硬件实验指导手册_盘古676系列100Pro+开发板》§2.1.3.4.4，
印刷页 48~49 (PDF 52~53)，已核对原理图和管脚表：

| SD 信号 | SPI 用途 | FPGA 焊盘 | MicroSD 接点 |
| --- | --- | --- | --- |
| CLK | SCK | F19 | 5 |
| CMD | MOSI | H14 | 3 |
| DATA0 | MISO | F18 | 7 |
| DATA1 | 不用 | F20 | 8 |
| DATA2 | 不用 | H17 | 1 |
| DATA3 | CS | H15 | 2 |
| SDDEF | 插卡检测 | G19 | 卡座开关 9 |

这五根线已加进 `boards/mes2l100hp/pins.csv` (SD_SCK/SD_MOSI/SD_MISO/SD_CS/SD_DET), 经 GPIO 矩阵接 SPI,
**默认就用板载卡槽** (要 2026-11-03 之后的位流)。也可以改用外接 SPI SD 模块: 编译时加 `-DSD_EXTERNAL`。

外接模块的接线 (`-DSD_EXTERNAL`) 定义在 `sw/bsp/board_sd.h`，换脚只改这个头文件：

| 模块端 | 仓库引脚名 | FPGA 焊盘 | 矩阵功能 |
| --- | --- | --- | --- |
| SCK / CLK | EXT29 | AA22 | 输出 2 SPI_SCK |
| MOSI / DI / CMD | EXT30 | AA23 | 输出 3 SPI_MOSI |
| MISO / DO / DAT0 | EXT31 | Y25 | 输入 1 SPI_MISO |
| CS / SS / DAT3 | EXT32 | AA25 | 普通 GPIO，低有效 |
| GND | GND | — | 必须共地 |
| VCC | 模块要求的供电 | — | 卡和 FPGA 信号均为 3.3 V |

EXT29~34、EXP35/36 已在 pins.csv 中，默认四脚未占用功放 AMP_*、星闪 WS_* 或相机 CAM_*。
这里的名字是仓库逻辑名，**不是 FMC 连接器针号**；接 GameShield/FMC 适配板时按该板原理图找同名网，
**默认四脚属于 L6 Bank，供电为 L6_VADJ，必须先核实为 3.3 V** (不是固定3.3 V的L4)。当前仓库没有这块适配板完整针号/供电资料，不能据此指定电源针号。
裸卡用 3.3 V，CMD/DAT 建议 10~47 kΩ 上拉；带稳压/电平转换的模块按其说明供电，禁止把 5 V 信号送入 FPGA。
SPI 被本驱动独占，不可同时使用 SPI LCD。接短线；读不稳可将高速分频从 /4 改为 /8。

## 驱动与文件系统

`sw/components/sd/sd.c`：模式 0，初始化 /128 (50 MHz 时 390.625 kHz)，读 /4 (12.5 MHz)。
CS 高时至少 80 个时钟，CMD0 → CMD8 → CMD55/ACMD41 → CMD58；SDSC 再发 CMD16=512。
CMD8 检查回显；支持 SDv1、SDv2 SDSC 和 SDHC (SDXC 卡若格式化 FAT32 也使用块地址)。
读只用 CMD17，SDSC 用字节地址，SDHC 用块地址，等待 0xFE token，取 512 字节并丢弃两个 CRC 字节。
初始化等待最多约 2 秒，读 token 等待约 250 ms，单字节 SPI 等待约 10 ms；错误后释放 CS。
不支持 MMC、SDIO、exFAT、CRC 校验、多块 DMA，也不自动重新初始化掉线的卡。

`pak.c` 与板子无关，用 `int read_block(uint32_t lba, uint8_t data[512])` 作为唯一块设备接口：

- 512 字节扇区的 FAT32，支持裸卷或 MBR 第一主分区，不支持 GPT/扩展分区。
- 只找根目录短文件名 `AMA     PAK`，跳过 LFN/已删除项/目录/卷标。根目录最多遍历 128 个簇，避免坏链死循环。
- 尊重 FAT32 活动 FAT 设置；检查 BPB、文件范围和整个文件的连续簇链，碎片或截断时挂载失败。
- 只保留一个 512 字节扇区缓存。挂载后按 `PAK 起始 LBA + 字节偏移/512` 读取，不再追 FAT。

选择 FAT32 而不是裸分区，是为了让用户直接复制文件。连续约束省去运行期簇映射，避免为音乐流加复杂文件系统。
**新格式化的空卡先复制 AMA.PAK 通常会连续，但不保证；驱动会验证。** 反复替换可能产生碎片，失败时先备份卡上内容，
重新格式化 FAT32 后将 PAK 作为第一个文件复制。挂载检查需遍历整条文件 FAT 链，大包会增加开机时间。
不支持运行中改写包；复制后安全弹出再插入板子。

## AMA.PAK v1

全是小端，扇区 512 字节，无压缩。包末尾和每个素材起点按 512 对齐，最多 64 项。
目录后的 payload 也从下一扇区开始；长度不包含扇区补零。只支持小于 4 GiB 的包。

| 文件位置 | 内容 |
| --- | --- |
| 0 | 8 字节魔数 `AMAPAK1\0` |
| 8 | uint32 版本=1 |
| 12 | uint32 目录项数 |
| 16 | uint32 包总字节数 (包含补齐) |
| 20~511 | 保留，写零 |
| 512 起 | 每项 64 字节，见下表 |

| 项内偏移 | 内容 |
| --- | --- |
| 0~23 | ASCII 名字，零结尾，最多23字节 |
| 24 / 28 | uint32 类型 (1立绘/2音乐/3音效) / 类型内编号 |
| 32 / 36 | uint32 payload 字节偏移 / 字节长度 |
| 40 / 44 | uint32 循环起始 / 结束样本编号 (音乐，结束不含；0表示不循环) |
| 48~63 | 保留，写零 |

编号按每类文件名排序从 0 开始，新增/改名可能改变编号；工具输出同名 `.json` 清单供查阅。
文件名去扩展名后必须是 ASCII、每类唯一。

### 立绘布局

现有 35 张基础图案占 24,512 字节，122 个不透明 RGB565 颜色。
`refmodel.py` 把基础图案约束到色号 1~127 (超过则量化)，0 透明，立绘独占 **128~255**。
每张立绘单独量化 128 色，alpha<128 的像素透明；无逐像素半透明。
基础图案生成时检查不进入最后 8 KiB，不使用保留图案编号。

选半分辨率方案：PNG 保持比例缩到 **64×96**，透明补边，硬件用 scale=32 (两倍) 显示 **128×192**。
一次只载一张；这比原分辨率 24 KiB 节约 16 KiB，代价是细节较少、需走旋转缩放渲染路径。
一次三精灵 (64×64 + 两个32×32)，每条立绘行最多两个精灵。

| payload 相对位置 | 内容 |
| --- | --- |
| 0~255 | 128 项 uint16 RGB565，对应硬件调色板 128~255 |
| 256~511 | 保留零 |
| 512~4607 | 上部64×64，8位色号逐行存 |
| 4608~5631 | 左下32×32 |
| 5632~6655 | 右下32×32 |

固定图案库字节偏移 57344~63487，图案编号 1000~1002。余下 2 KiB 暂不用。
`gfx_portrait_load(id)` 同步读取并上传调色板/图案，同 id 不再读写；id<0 隐藏。
`gfx_portrait(x,y,alpha)` 每帧追加三精灵，x/y 是左上角，alpha=0~16。
换角色时应在场景切换中调用 load：上传期间不保证正在显示的旧立绘没有撕裂，也不能保证音乐持续无欠载。
失败会隐藏立绘。电脑版 `media_pc.c` 从同一个 PAK 解码 RGB565/色号，经 SDL 贴图；不再重新量化。
现有 stats 帧转储/参考模型导出仍只带基础 ROM 素材，未把外部立绘打入转储；SD立绘请用PC直接打开PAK预览。

### 音乐与 PCM

ffmpeg 转为 signed PCM8、16 kHz、单声道，无文件头。长度补到4样本对齐。
可在音频旁放同名 `.loop.json`：`{"start": 0, "end": 32000}`，单位是16 kHz样本，两者都须4对齐。
不提供 sidecar 时播放一次。提供时先播 [0,end)，之后重复 [start,end)。

`game/assets/sfx/` 的 WAV/OGG/MP3 转为同格式，截到前1秒，无循环点，类型为3。
板上挂载后与PC启动时一次读入固定12 KiB池，放不下的跳过并输出名字，后续播放不读卡。
音效名对应 `sound.c` 的 `wav` 字段，缺失就回退合成；用法和音量见 [game/README.md](../game/README.md)。

`bgm_play(id)` 替换音乐源；`bgm_stop()` 只停止音乐源，FIFO中的混音尾巴和音效继续。
两端使用同一 `core/mix.c`，每帧 `bgm_frame()` 只补到约800样本，保持约50 ms缓冲。
循环仍为先播 [0,end)，之后重复 [start,end)；音乐读失败或结束后音效继续。
暂停菜单期间也调用 frame。SD同步读取/超时、立绘上传仍可能跨帧并导致欠载。
PC通过 `audio_sdl.c` 的PCM模型输出，不另外创建音频设备。

## 验证与上板

```sh
uv run game/tools/pack.py --demo --assets game/build/demo-assets
make -C game check-sd        # 需要 C 编译器、mkfs.fat (dosfstools)、ffmpeg
make -C game
make -C game check-core
./ama build sd_test -b mes2l100hp
./ama run sd_test -b mes2l100hp  # 插上外接模块, 把包拷到卡根目录后运行
./ama build game -b mes2l100hp
riscv64-elf-size build/fw/mes2l100hp/game/app.elf
python game/tests/cpu_perf.py   # 可选: 只模拟CPU，不生成位流
```

`sd_test` 输出 SDSC/SDHC、PAK 版本、项数、字节数、起始 LBA 和素材0长度。
宿主测试用 mkfs.fat 生成真实64 MiB FAT32镜像，在空卷中放入连续 AMA.PAK；测试夹具自行写目录和FAT，不用root挂载。
同一份 `pak.c` 分别通过文件读扇区和内存镜像块设备运行；另编译未改的 `sd.c` 用字节级卡响应模拟检查协议，
编译板上 `media.c` 用 mmap 显示地址和2048样本FIFO检查上传、连续读和循环。
不包含真实卡的电气/时序验证；用户上板时还应看音乐欠载计数、开场上传时间和游戏串口 `cpu max`。

## ROM

合并后 game 仍是 -O2 (全局 -Os 会让每帧慢约 3 倍, 见下)。ROM 够用是因为开机素材改成压缩存放
(`refmodel.py` 的 `lz_pack`, 25.7 KB → 4.4 KB, `gfx_hw.c` 开机解压), 2026-11-03 game `.text` 46.5 KB / 62 KB。

同一CPU RTL、零额外总线等待、320弹幕、8帧 step/draw/板上精灵表提交：
-O2 平均141,543、最大141,696拍；-Os 平均432,636、最大432,807拍，平均3.06倍。
该场景无立绘、SD、手势网络、HDMI轮询或视频等待，不能据此保证整机最坏帧预算；
上板以现有串口 `cpu max` 为准。开场加载立绘/进关预填音乐可能跨帧，属于同步场景加载。

验证：12项宿主测试通过；`make -C game`、`check-core`、`check-sd`，SPI RTL单项，CPU RTL性能对比和SDL无窗口截图均通过。
当前隔离环境 uv 默认缓存只读且 DNS 不通，构建用现有 Python 依赖 (`make UV=python`) 和缓存里的 ama Python 环境运行同一CLI。
没有构建位流，没有实体SD/功放验证。后续需合入A/B，并上板确认模块供电、读卡可靠性、音乐欠载和完整帧拍数。
