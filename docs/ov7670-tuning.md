# OV7670 在线调参方案（UART 实时改寄存器）

目标：在电脑上改 OV7670 的曝光、增益、白平衡、颜色格式和显示侧增益，**改完下一帧就在 HDMI 上看到**，
不用每次改一个数字都走一遍 PDS 综合（约 10 分钟）。本文是方案设计，不是已实现的功能；
现状见[上板验证结果](ov7670.md#上板验证结果)。

## 结论

- **能做**：OV7670 的曝光、增益、白平衡、gamma、亮度、颜色格式、字节顺序都是 SCCB 寄存器，
  全部可以实时改。显示侧的小窗位置和数字增益也可以。
- **不能做**：**聚焦**。OV7670 模块是机械对焦环，没有对应寄存器，只能手拧镜头。
- **真正的障碍不在 UART**，而在两处 RTL/板级现状：SCCB 控制器没有 CPU 接口，
  相机模式下 SCL/SDA 被顶层从 GPIO 矩阵手里独占（见下一节）。
- **UART 侧现成够用**，一行 RTL 都不用改。

## 参数分类

| 想调的东西 | 能软件实时改吗 | 依据 |
| --- | --- | --- |
| 曝光（AEC）、增益（AGC）、白平衡（AWB） | 能 | `COM8`(0x13) = 0xE7 已在本仓库的 30 条表里 |
| AGC 上限、AEC 目标区间、亮度 | 能 | `COM9`(0x0F)、`AEW`(0x24)、`AEB`(0x25)、`BRIGHT`(0x55) |
| 白平衡增益 | 能 | 0x6C~0x6F（蓝/红/绿/绿） |
| gamma 曲线 | 能 | 0x7B~0x8B，17 点 |
| 颜色格式（RGB / YUV422）、RGB565 范围、字节顺序 | 能 | `COM7`(0x12)、`COM15`(0x40)、`TSLB`(0x3A) |
| 显示侧亮度增益、小窗位置 | 能 | `ov7670_vga` 的 `brighten()`；`video.v` 的 WINDOW |
| **聚焦** | **不能** | 机械对焦环，无寄存器 |

寄存器地址取自 [ov7670_sccb_init.v](../rtl/vision/ov7670_sccb_init.v) 的表和注释。
表里的 `COM9 = 0x60`、`AEW = 0x75`、`AEB = 0x63` 是 OV7670 的常见初始化经验值，
**本仓库只是照抄，效果并没有验证**（画面仍然偏暗就是这个原因之一）；要再深入
（比如时钟分频、窗口寄存器）必须先对着 OV7670 数据手册确认地址含义，不要凭猜测往总线上写。

## 现状：三个必须知道的事实

### 1. SCCB 控制器没有 CPU 接口

[ov7670_sccb_init.v](../rtl/vision/ov7670_sccb_init.v) 的端口只有
`clk / rst_n / sda_in / scl_low / sda_low / done / error`，是一台上电跑完 30 条就停的自动机。
30 条寄存器写在 `function register_address` / `register_value` 里，是常量。CPU 只能看它成没成
（LED1 / LED2），改不了任何一个数。

### 2. 相机模式下 SCL/SDA 被顶层独占

[mes50hp_top.v](../boards/mes50hp/mes50hp_top.v) 的 `g_camera_scl` / `g_camera_sda` 分支
直接 `assign io[n] = camera_scl_low ? 0 : 1'bz`，**绕过了 SoC 的 `io_o` / `io_oe`**。
所以固件就算想 bit-bang，也碰不到 J8_21 / J8_22 这两个脚。

引脚本身是 `inout`（[pins.csv](../boards/mes50hp/pins.csv) 的 J8_21 = AB9、J8_22 = Y9），
且不在反向掩码 `IO_IN_N_MASK` 里，所以放回 GPIO 矩阵后 `io_read` 读到的就是真实电平，不需要取反。

### 3. UART 侧已经够用

| 事实 | 位置 |
| --- | --- |
| 接收侧有 **16 字节 FIFO**，`STATUS.bit1` = FIFO 非空，写 STATUS 取走一个字节 | [uart.v](../rtl/perips/uart.v) |
| 固件已有非阻塞收字节 `uart_getc` | [uart.h](../sw/drivers/uart.h) |
| 一个 4 字节命令包远小于 16 字节 FIFO，不会溢出 | 本方案 |
| PC→板子串口协议已有先例（首字节最高位置 1 当包头） | [pad.h](../game/board/pad.h)、[pad.py](../tools/ama/pad.py) |

带宽完全不是问题：115200 下一包 4 字节约 0.35 ms；一次 SCCB 写约 0.3 ms（100 kHz）；
一帧 16.7 ms。**改完下一帧就能看到**。

## 三条路线

| 路线 | 做法 | 改动量 | 风险 |
| --- | --- | --- | --- |
| **A（推荐）** | 顶层加一个参数，把 J8_21/22 在相机模式下交回 GPIO 矩阵；固件用软件 SCCB 直接写寄存器 | RTL 约 10 行 + 一个 `app.toml` 参数 + 新固件文件 | 低 |
| B | 把 `ov7670_sccb_init` 扩成 CPU 可写的寄存器接口（addr / data / start / busy / ack） | 要新增第 7 个 RIB 从设备 | **高**：[soc_top.v](../rtl/soc_top/soc_top.v) 是 `PERIPH_N = 6`，6 个槽位（UART / SPI / MATRIX / SYSCTL / VISION / NN）**已经全用满**，得动地址译码 |
| C | 不做协议，固件里单字节命令 = 写一个寄存器 | 几乎为零 | 扩展性差，只适合当 A 的第一步 |

**选 A**：不碰总线结构，复用已经存在的 bit-bang 代码，引脚本来就在 `io` 总线上，
`PIN_J8_21` / `PIN_J8_22` 的固件宏也已经生成好了（[mes50hp_pins.h](../sw/bsp/mes50hp_pins.h)）。

### 关于"复用 i2c.c"的一个准确说明

[i2c.c](../sw/drivers/i2c.c) 目前**只有 16 位寄存器地址**的函数（`i2c_write_reg16` /
`i2c_read_reg16`，低字节先发，是 MS7210/MS7200 的约定）。OV7670 是 **8 位寄存器地址**，
所以不能直接调用。`start` / `stop` / `write_byte` / `read_byte` 都是 `static`，
复用方式是在 `i2c.c` 里补一个 8 位地址的写函数（复用这几个 helper），或者新建一个 `sccb.c`。
两者都只增加几十行。

SCCB 写序列（单相）：起始 → 器件写地址 → ACK → 8 位寄存器地址 → ACK → 数据 → ACK → 停止。
器件写地址是 8 位形式的 **0x42**（7 位 0x21 左移一位），读是 0x43。
**读**在 SCCB 里是两相（写完地址要 stop，再 start 发读地址），和 I2C 的重复起始不同，
所以第一阶段只做写，读回校验放到后面。

## 路线 A 的设计

### RTL：引脚归属二选一

在 [mes50hp_top.v](../boards/mes50hp/mes50hp_top.v) 增加一个顶层参数
（暂定 `OV7670_SCCB_SOFT`，默认 0 = 保持现在的 RTL 自动配置）：

| 参数 | J8_21/22 归谁 | 30 条表 | 适用 |
| --- | --- | --- | --- |
| `OV7670_SCCB_SOFT = 0`（默认） | RTL 的 `ov7670_sccb_init` | 上电自动写 | 现在的相机位流，行为完全不变 |
| `OV7670_SCCB_SOFT = 1` | GPIO 矩阵（CPU） | 不写，由固件负责 | 在线调参 |

改动要点：

1. `g_camera_scl` / `g_camera_sda` 两个分支加 `&& !OV7670_SCCB_SOFT` 条件，
   让这两脚落回后面的 `g_inout` 分支，由 SoC 的 `io_oe` / `io_o` 驱动。
2. `OV7670_SCCB_SOFT = 1` 时**不要实例化** `ov7670_sccb_init`，避免两个主设备同时驱动总线。
3. LED 语义跟着改：LED1 = 最近一次 SCCB 写成功，LED2 = 最近一次写失败（NACK），
   LED3 保持"收到过完整帧"。这三只灯在没有串口时仍然是唯一的观测手段。
4. 这个参数要放进 `sw/app/<程序>/app.toml` 的 `params`，按 [ov7670.md](ov7670.md) 的方式
   重新 `fpga build --app ...` + `fpga program`。**参数会算进 `hwid`**，所以带不带它会生成两个不同的位流。

> 为什么不用 "固件自己重配 io 方向" 绕过：顶层那个 `assign` 是**另一套驱动源**，
> 只要 `OV7670_MONITOR=1` 就一直在驱动 `io[18]` / `io[19]`。必须在顶层二选一，不能靠软件绕过。

### 固件：命令循环

在相机 app 的 `main()` 里，`board_hdmi_init()` 之后加一个**非阻塞**循环：
每轮 `uart_getc` 收字节，凑齐一个包就执行，执行完顺手刷新 LED1/LED2。
不阻塞是必须的，否则调参期间画面扫描会受影响（扫描是硬件做的，但 LED8 的闪灯和将来的读回要靠 CPU）。

固件需要的三样东西：

| 东西 | 来源 |
| --- | --- |
| 8 位寄存器地址的 SCCB 写 | `i2c.c` 里补一个函数（复用 `start` / `write_byte` / `stop`） |
| SCCB 引脚定义 | `PIN_J8_21`（SCL）、`PIN_J8_22`（SDA）；`half_cycles = SYSCLK_HZ / 200000`（= 100 kHz），和 [board_hdmi.h](../sw/bsp/board_hdmi.h) 里 HDMI 芯片的写法一致 |
| 30 条默认值（可选） | 把 RTL 里那张表抄一份到固件，做"恢复默认"命令（`cmd 2`） |

### 协议：4 字节定长包

风格照抄 [pad.h](../game/board/pad.h)：**首字节最高位置 1** 当包头，定长，不做转义。

PC → FPGA：

| 字节 | 含义 |
| --- | --- |
| 0 | `0x80 \| cmd`，cmd 见下表 |
| 1 | `reg`：8 位寄存器地址 |
| 2 | `value`：写入值 |
| 3 | `xor`：前 3 字节异或，用来丢包检测 |

| cmd | 作用 | 回包 |
| --- | --- | --- |
| 0 | 写寄存器 `reg = value` | `'K'` 成功 / `'N'` 无 ACK |
| 1 | 读寄存器 `reg`（第二阶段实现） | `'K'` + 1 字节数据 / `'N'` |
| 2 | 重放默认表（恢复出厂） | `'K'` |
| 3 | 设置 SCCB 分频：`reg` 高字节 + `value` 低字节 = `half_cycles` | `'K'` |
| 4 | 心跳 / 版本 | `'K'` + 一个版本字节 |
| 5 | 快捷开关：`value` bit0 = AEC、bit1 = AGC、bit2 = AWB（写 COM8） | `'K'` / `'N'` |

回包只用可读 ASCII（`'K'` / `'N'` / `'?'` 表示包错），在 `./ama monitor` 的终端里能直接看懂，
不需要额外解析工具就能手工调试。

**不要把长串 `0x00` 发过来**：`UART_BREAK_RESET = 1` 的位流会把连续约 10 ms 低电平
（115200 下约 115 个 `0x00`）当成 break 复位。相机 app 现在设的是 0，但协议本身也不该依赖这一点。

### PC 端工具

## 硬件前提（必须先解决）

串口是整件事的前置条件，和代码无关：

| 项 | 现状 | 要做的 |
| --- | --- | --- |
| UART 引脚 | RTL 已在 `R9`（TX）/ `R8`（RX），即 `io[57]` / `io[58]`（[pins.csv](../boards/mes50hp/pins.csv)） | 不用改 |
| PC 连接 | 上板记录写的是**板载 CP2102 未接线**，所以固件 `printf` 一直看不到 | 接上 CP2102 的 USB 口，或用 **3.3V** 的 USB-TTL 直接接 R9/R8（**别接 5V**） |
| 验证方法 | — | `./ama monitor -b mes50hp` 能看到 `OV7670 VGA monitor ready` |

串口不通，后面的所有步骤都无从验证。

## 风险与对策

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| 两个主设备同时驱动总线 | RTL 自动机 + 固件 bit-bang | 用 `OV7670_SCCB_SOFT` 参数互斥，不要同时使能 |
| SCL 是推挽驱动 | [i2c.c](../sw/drivers/i2c.c) 里 SCL 用 `io_dir(OUTPUT)` 推挽输出，SCCB 严格来说应开漏 | 单主 + FPGA 内部上拉，实测可接受；要严格就把 SCL 也改成"释放式"（`io_dir(INPUT)` 拉高） |
| 只写不读，无法确认生效 | 现在的 RTL 自动机就是这个问题（有 ACK 不代表寄存器有效果） | 第二阶段加 `cmd 1` 读回 |
| 改参数瞬间半帧 | 单帧缓冲 | 可接受；要无缝就得上双缓冲（RAM 再翻一倍） |
| 位流版本号变化 | `params` 参与 `hwid` 计算 | 按 [ov7670.md](ov7670.md) 重新 build / program，别指望 `--force` |
| 160x120 看不清细节 | 目前是 4x4 抽样、左上角原尺寸 | 需要精调时再加一个"1:1 裁一块原尺寸显示"的开关（另一处 RTL 改动） |
| 寄存器含义靠猜 | 本仓库只验证过 30 条表里的那些 | 表外的地址先查 OV7670 数据手册，再往总线上写 |

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| M0 | 接好串口（不改任何代码） | `./ama monitor -b mes50hp` 打印 `OV7670 VGA monitor ready` |
| M1 | RTL 放开 J8_21/22 + 固件"收一个字节命令 → 写一个寄存器" | 改 `COM7` / `TSLB`，屏幕上立刻看到颜色变化 |
| M2 | 4 字节包协议 + 命令行工具 | `./ama tune camera --set 0x40=0xD0` 回 `'K'`，画面变化 |
| M3 | 滚条界面 + 用它定位"红绿互换"和"偏暗" | 两个问题各有一个确定性结论（见下节） |
| M4（可选） | 把调好的值写回 30 条表，去掉运行时依赖 | 不带 `OV7670_SCCB_SOFT` 的位流也有正确画面 |

## 用它来定性两个已知问题

这正是当前两个"只能盲试"的问题最需要的工具。建议的操作顺序（**每一步只改一个寄存器**，
否则分不清是哪个起的作用）：

| 目标 | 先动 | 期望 |
| --- | --- | --- |
| 红色显示成绿色 | `COM7`(0x12)：在 RGB(0x04) 和 YUV422 之间切 | 如果切到 YUV 画面结构明显不同 → 说明原来确实是 RGB，问题在字节配对（`TSLB` 0x3A 的位序 / MSB 先后） |
| 同上 | `COM15`(0x40)：0xD0（全范围）↔ 0x10（受限范围） | 排除是输出范围导致的截断 |
| 同上 | `TSLB`(0x3A)：0x04 ↔ 0x01 ↔ 0x00 | 判断是不是字节顺序错位把 G 的位段当成了 R |
| 画面仍偏暗 | `COM8`(0x13)：确认 AEC/AGC/AWB 真的开着（bit2/bit1/bit0） | 若读回发现没开，说明之前的 30 条表写入没真正生效（ACK 假通过） |
| 同上 | `COM9`(0x0F)：AGC 上限 0x60 往上调 | 看亮度是否跟着变，从而判断增益路径通不通 |
| 同上 | `AEW`(0x24) / `AEB`(0x25) / `BRIGHT`(0x55) | 逐个扫，确认哪个寄存器真起作用 |

## 不做的事

- **不通过软件调焦**：机械件。要自动对焦得换带 VCM 的模组。
- **不在第一阶段做 SCCB 读**：两相时序和 I2C 不同，先只写，等写路径稳定再加。
- **不动 RIB / `PERIPH_N`**：路线 B 才需要，收益不如 A。
- **不做分辨率切换**：0x17/0x18/0x19/0x1A/0x32/0x03 这些窗口时序寄存器一旦改错，
  现在这套采样逻辑（假设 640x480）会直接失效，风险远大于收益。
