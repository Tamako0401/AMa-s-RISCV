# 显示扩展方案 (草案)

现有显示见 [video.md](video.md): 320x240 放大到 640x480, 背景 + 64 个 16x16 精灵, 逐行现画。
这里是换到盘古 100K 之后的扩展计划, 2026-10-23 讨论整理, 还没开始实现。依据: 审查
[04_video.md](review/2026-10-21/04_video.md)、[07_tradeoff.md](review/2026-10-21/07_tradeoff.md)。

## 目标

- 两个游戏: 东方式弹幕 (主线) 和水果忍者式 (第二个)。输入是手的位置 + 握拳 / 张开 ([hand-model.md](hand-model.md))。
- 演示效果优先: 16:9 铺满屏幕、弹幕发光、刀光顺滑、文字清晰、摄像头画面和游戏同屏。
- 有能量化的硬件加速 (赛题高阶任务看加速比、资源、时序)。

| 游戏 | 对象 | 需要的能力 | 瓶颈 |
| --- | --- | --- | --- |
| 东方式 | 300~500 发小弹 (8x8、16x16) | 加法混合 (发光); 弹的朝向用预转好的 16 个角度的图 | 对象数、CPU 每帧更新 |
| 水果忍者式 | 20 个以内大对象 (32~64 点) | 旋转缩放、alpha (果汁淡出)、刀光 | 每行要画的像素数、旋转采样 |

## 画面规格

- 输出 1280x720@60 (像素时钟 74.25 MHz, 经 MS7210)。游戏按 **640x360** 画, 每点放大成 2x2。
  参照: 东方 Windows 版是 640x480 (游戏区 384x448), PC-98 版 640x400 且只有 16 色; 水果忍者最早在 480x320 的手机上。
- 布局照东方原作: 中间竖长的游戏区 (约 300x360), 两侧是侧栏, 放摄像头小窗、分数、bomb 数。
  这样小窗不会盖住游戏 (审查指出现在的小窗盖住所有精灵)。

## 架构: 逐行渲染 + 多图层

两种做法 (游戏机历史上: FC / SFC / GBA 是前者, PS1 是后者):

| | 逐行渲染 (现画现播, 现有架构) | 帧缓冲 (先画好再播) |
| --- | --- | --- |
| 怎么做 | 每行显示前才算这一行, 画进一条行缓存; 两条行缓存轮流 (一条在播, 一条在画) | 一整张画面存在内存里, 显示端像 DMA 一样不停读出去; 画图的一边 (CPU 或 blitter) 随时往里写; 双缓冲在场消隐时交换 |
| 存储 | 几 KB | 640x360、8 位色双缓冲约 460 KB, 是片上 RAM 的约 2/3; 否则要上 DDR3 |
| 时限 | 每行有硬截止时间, 画不完这行出错 | 整帧画完即可, 画不完掉帧 |
| 风险 | 低, 延续已上板的结构 | 帧缓冲放片上挤占 CPU / CNN; 放 DDR3 是审查标的 L 级风险 |

**选逐行渲染, 重写渲染后端。** 输出时 4 层逐像素叠起来, 每层分辨率、色深可以不同:

```
文字层   1280x720 原生   VGA 文本模式: 8x16 格的字符编号 (160x45 格, 约 7 KB) + 1 位字库 (约 4 KB)
刀光层   1280x720 原生   不存图: 只存几十个线段端点, 每条物理行现算覆盖哪几段, 边缘按距离淡出 (抗锯齿)
精灵层    640x360 x2     旋转缩放、alpha / 加法混合; 水果、弹幕、粒子、果汁
背景层    640x360 x2     图块卷轴 (沿用现有)
侧栏小窗                 摄像头 160x120, 放在侧栏
```

渲染后端要改的 (审查 04 的建议 + 本次讨论):

- **行缓存改存 RGB565** (一行 1.3 KB): 才能做混合 (读出底下的颜色、算、写回)。现在存的是调色板编号, 没法混合。
- **对象按 Y 分桶**: 每行只看和这一行相交的对象。现在每行扫一遍全部 64 个属性, 扩到 512 个光扫描就要约 1000 拍。
- **一拍画 8 个像素** (span), 透明像素关掉写使能。旋转缩放单独一条逐像素采样的通路 (每像素 u、v 只做加法)。
- **精灵表双缓冲, 场消隐时原子切换**: CPU 写后台那份, 写完提交。现在没有, demo 已出现混帧。
- **每行用了多少拍、有没有超时** 做成计数器寄存器: 调试用, 演示时也能证明最坏情况画得完。
- 现有 320x240 引擎保留, 新后端出问题能退回。

刀光和水果的画法:

| 效果 | 画法 |
| --- | --- |
| 刀光 | 刀光层: 手的轨迹变成一串四边形, 每行算出覆盖的 x 范围再填 (扫描线多边形填充), 中间亮、边缘淡出。<br>退路: 沿轨迹盖一串越来越小、越来越淡的光点精灵 (印章法), 只用精灵层 |
| 切开的两半 | 每种水果预先画好沿水平线切开的上下两半, 按刀的角度整体旋转后画 |
| 果汁、粒子 | 预先画好的溅射图 / 小光点, 精灵层带 alpha 或加法混合, 慢慢淡出 |

## 软硬件分工

软硬件都是自己写, 同一件事可以放三个地方:

| 放在哪 | 例子 | 速度 | 灵活性 |
| --- | --- | --- | --- |
| 软件 | C 更新弹幕位置、判碰撞 | 慢 (审查估 500 发约占半帧) | 最高, 改玩法只改 C |
| 通用硬件 | 精灵引擎、混合、刀光层: 两个游戏都用 | 快 | 中 |
| 专用硬件 | 弹幕单元: 硬件做 位置 += 速度、出界回收、碰自机 | 最快 | 只适合弹幕 |

规则: 两个游戏都要的放通用硬件; 只有一个游戏要的先放软件, **在板上量过确实慢**再考虑专用硬件。
弹幕单元是最可能做的专用硬件, 因为它的加速比好量 (同样 500 发, 软件和硬件各多少周期)。

软硬件之间的接口 (寄存器、精灵表格式) 先在 Python 参考模型里定下来; C 和 RTL 照接口各自推进, 都和 Python 比对。
以后把某个功能从软件搬进硬件, 只要接口不变, 游戏代码基本不动。

## 预算 (估计, 待验证)

新板 PG2L100H 的数字来自选型表, 未核实: 块 RAM 155 x 36 Kb ≈ 700 KB, 乘法器 240 个。

| 存储 | 估计 |
| --- | --- |
| CPU ROM + RAM (ROM 去掉重复的那份后) | 100 多 KB |
| 精灵图案库 | 16~64 KB, 看画风 |
| 行缓存 (RGB565, 两条) + 精灵表 (双缓冲) + Y 分桶表 | 10~20 KB |
| 文字层 + 字库 | 约 11 KB |
| 摄像头小窗 | 19 KB |
| 手势 CNN | 权重十几 KB, 激活按行缓存几十 KB |
| ILA (赛题要求) | 十几 KB |

每行时间: 720p 一条物理行 22.2 µs, 一条逻辑行 (两条物理行) 44.4 µs; sys_clk 50 MHz 时约 2200 拍, 100 MHz 时约 4400 拍。
要在这段时间里画完 640 个点的背景 + 这一行所有对象。

DDR3 (几百 MB, 但一次访问要等几十拍、要控制器 IP 和新时钟域): 第一版不用。
图案库放不下时再把它当素材仓库, 按需搬进片上缓存。

## 要验证什么

写 RTL 之前, 先用 Python 参考模型 (给定精灵表、图层内容 -> 画出一帧) 回答下面这些问题。

| 问题 | 怎么验证 | 通过条件 |
| --- | --- | --- |
| 640x360 放大到 720p, 刀光、果汁看着够不够细 | 用 Python 模型画几张水果和弹幕的典型画面, 放大成 720p, 在真显示器上全屏看; 对比刀光放精灵层 / 刀光层、有没有软边缘 | 主观可接受; 决定刀光层值不值得做 |
| 每行画得完吗 | Python 模型按硬件的代价 (每个对象几拍、每 8 点一拍、旋转每点几拍) 数每行用了多少拍; 场景用两个游戏最坏的情况: 弹幕最密的一帧、几个大水果叠在同一行 | 最坏一行 < 每行可用拍数 (留余量, 比如 80%); 得出 sys_clk 要 50 还是 100 MHz、每行最多几个对象 |
| 存储装得下吗 | 按选定的参数 (对象数、图案库大小、色深) 列表, 再按块 RAM 的实际拼法 (宽、深取整) 算 | 总量 < 片上 RAM 的约 80%, 给 CNN、ILA 留位置 |
| 接口够不够两个游戏用 | 两个游戏的 C 版 (电脑后端) 直接用这套精灵表和图层接口写 | 不需要为某个游戏临时加特例 |
| 色深怎么定 | 比较 调色板 256 色 / RGB565 下混合 (发光、淡出) 的效果 | 选够用的最小色深 |
| CPU 跟不跟得上 | 不能用 Python 量: 用 C 写弹幕更新, 在仿真或板上数周期 | 500 发在一帧内留出足够余量; 否则做弹幕单元 |
| 新板能出 720p、跑得到 100 MHz 吗 | 板上: 现有 SoC 改成 720p 时序, 看 MS7210 出图; 综合后看时序 | 出图稳定; 所有时钟 WNS ≥ 0 |

前五项在电脑上做, 第六项要等 C 和仿真, 第七项要上板。

## 游戏怎么写

两个游戏都自己用 C 写。现成开源项目只能参考, 移植约等于重写: 我们没有浮点单元 (坐标用定点数、三角函数查表)、
没有 GPU 和帧缓冲、没有操作系统 (对象用静态数组)、内存只有几十到一百多 KB。

- [Taisei Project](https://github.com/taisei-project/taisei): C11 + SDL3 + OpenGL 的东方同人游戏, 代码 MIT,
  素材 CC-BY-4.0 / CC0。靠着色器出效果, 不能移植; 参考弹幕花样和代码组织, 素材按单个文件的授权、注明出处后也许能借。
- [TigermothGBA](https://pmprog.itch.io/tigermoth): GBA 上用 C 写的弹幕游戏 (未完成, 授权没核实)。
  GBA 也是图块 + 精灵、没有帧缓冲, 看它怎么在这种硬件上组织弹幕。
- 水果忍者类没找到 C 的开源实现。

规模估计: 东方式 1500~3000 行 C, 水果忍者式 1000~2000 行; 代码不难, 花时间的是弹幕设计、手感和素材。
`model/play.py` 约 400 行已经有核心玩法 (自机、三种弹幕、碰撞、bomb、重开), 可以照着写。

**同一份 C 代码在电脑和板子上都能跑**: 游戏只调用自己定义的接口 (设精灵、读手的位置、等下一帧)。
电脑后端用 SDL 实现 (手的输入来自 MediaPipe 或鼠标), 在 Mac 上全速调玩法和手感; 板子后端就是写显示寄存器、读视觉寄存器。
验证显示预算要的场景, 从电脑上跑的 C 游戏导出精灵表, 交给 Python 参考模型数每行用了多少拍。

素材: 先用几张简单的图占位, 以后用图像生成脚本出图再挑; 需要一个 Python 工具把 PNG 转成调色板 / 图集 / `.hex`。
人物和名字不直接用东方的, 做"东方风格"的原创内容; 借用素材按授权注明出处, 并按比赛的开源复用要求披露。

## 实施顺序

1. 新板上让现有 SoC 输出 720p (只改时序和放大倍数), 验证 MS7210 和时钟。
2. Python 参考模型 (渲染一帧、数每行拍数), 加上 C 游戏的电脑后端; 回答上表前五项, 定参数和接口。
3. RTL: 新渲染后端 (RGB565 行缓存、Y 分桶、span), 用仿真截图和 Python 模型逐像素比对; 对不上再看波形。
4. 文字层、刀光层。
5. 量 CPU, 决定要不要弹幕单元。
6. 最后加分项: 声音 (蜂鸣器 PWM 放音乐, 或 HDMI 音频, 要先查 MS7210 是否支持 I2S 输入)、数码管计分。
