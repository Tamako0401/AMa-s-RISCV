# 视觉输入

`rtl/vision/`: 把输入的图像 (现在是 HDMI 接收芯片, 以后换 OV5640) 一边收一边处理, 不存整帧。
现在做到: 收图 -> 4x4 均值缩小成 160x120 -> 存成小图, 在视频输出的小窗里显示 (见 [video.md](video.md));
同时找画面里的颜色标记, CPU 读寄存器得到它的位置; 也可按 CPU 请求直接送入 handnet 推理。

```
MS7200 ──> hdmi_rx_adapter ──> crop ──> box4 ──┬──> window_store ──> 小窗 (video.v 读)
                                               ├──> color_track ───> 寄存器 (CPU 读)
                                               └──> 小异步 FIFO ──> NN 输入 RAM ──> handnet
crop 整帧验证 ────────────────────────────────────> 抓帧成功后自动推理 (系统时钟)
(以后换相机: OV5640 ──> ov5640_adapter, 接在 crop 前面)
前端流水线在 vin_pclk 下; 小窗读口在输出扫描时钟下, NN RAM 和 CPU 寄存器在系统时钟下
```

## 像素流

各级之间都用同一组信号, 换算法只换中间某一级, 换相机只换适配器:

| 信号 | 意思 |
| --- | --- |
| `valid` | 这一拍有一个像素 |
| `sof` | 帧的第一个像素 (和 valid 同拍) |
| `eol` | 行的最后一个像素 (和 valid 同拍) |
| `data` | 像素, RGB888 (`[23:16]` R) |

- 像素按行从左上到右下; 两个像素之间可以有任意个空拍 (valid = 0)。
- 位置由下游自己数: sof 归零, 每个 valid 列加 1, eol 之后换行。
- 每级输出都是寄存器, 级与级直接相连。

## 各级

| 模块 | 做什么 | 资源 |
| --- | --- | --- |
| `hdmi_rx_adapter` | MS7200 的 de + RGB -> 像素流。de 断开超过 4096 拍算场消隐, 不管同步极性 | 几十 LUT |
| `crop` | 每帧测有效宽高, 稳定后自动居中裁 640x480, 验证整帧后提交 | 计数、比较和快照, 无 RAM |
| `box4` | 4x4 均值 (步长 4 的均值卷积): 横向每 4 点累加, 纵向一行 W/4 个部分和存 RAM, 满 4 行输出 | 一块 RAM |
| `window_store` | 160x120 RGB332 双缓冲; 只发布验证通过的整帧, 读口在输出像素时钟 | 20 个 2048x8 块 |
| `color_track` | 每个点算 YCbCr 的 Cb、Cr, 和目标色都差不超过容差算命中; 一帧累加命中的个数和 x、y 之和 | 几个常数乘法和累加器 |

## 寄存器 (0x4000_5000, 外设子总线)

| 偏移 | 名字 | |
| --- | --- | --- |
| 0x00 | COLOR | 读写, 整字写: `[7:0]` Cb, `[15:8]` Cr, `[23:16]` 容差 |
| 0x04 | COUNT | 只读, 上一帧命中的点数 |
| 0x08 | SUM_X | 只读, 命中点的 x 之和 (160x120 里) |
| 0x0C | SUM_Y | 只读, 命中点的 y 之和 |
| 0x10 | FRAME | 只读, 每出一帧结果加 1 |
| 0x14 | CENTER | 只读, 画面正中 8x8 个点的平均颜色: `[7:0]` Cb, `[15:8]` Cr (标定用) |
| 0x18 | INPUT_SIZE | 只读, 最近一个完整测量帧: `[11:0]` 有效宽, `[27:16]` 有效高, 其余为 0 |
| 0x1C | INPUT_STATUS | 只读, bit0 尺寸支持且各行等宽, bit1 连续两帧尺寸一致且支持, bit2 不支持/坏帧 |

- 重心 = SUM / COUNT, 除法由软件做: `sw/drivers/vision.h` 的 `vision_find()`, 它会重读直到三个数来自同一帧。
- 颜色统计和小窗都在下一输入帧 SOF 验证前一整帧后发布; 过渡帧/坏帧不更新结果或 FRAME。
  测量宽高与状态以同一个帧边界快照跨到系统域; `INPUT_SIZE` 的宽、高在一次 32 位读取里一致。
  bit0=1、bit1=0 表示尺寸支持但正在等稳定; 初始状态全 0, 不代表已有信号。
  数据停止后寄存器保留旧值, 最后一帧仍需下一 SOF 才发布; 没有新增断流超时。改 COLOR 的那一帧结果仍可能不准。
- 颜色怎么选: 上板时标定 (标记放在画面正中, 读 CENTER 设成目标色, `video_demo` 里是串口命令 `c`);
  事先估计用 `model/color.py` 在画面上点选, 硬件和它逐位相同。

盘古实测 (2026-10-21, `ama fpga report --board mes50hp`): 整个视觉输入 581 LUT / 493 FF / 3 DSP, 块 RAM 297 Kb
(其中颜色跟踪 278 LUT / 2 DSP)。这是改动前的数字, 小窗占 288 Kb (16 块),
因为单份 19200 深度补成 32768。全片基线 119.5/134 块 DRM18K。

本次资源是静态估计, 未综合: 尺寸测量/动态裁剪/快照 **+0 块 RAM**; 颜色统计延后发布 **+0 块 RAM**。
小窗改为两份后台/前台, 每份 `ceil(19200/2048)=10` 个 2048x8 RAM (预计每块用 1 个 DRM18K),
总 **20 块**, 相对原先 16 块 **净增 4 块**, 净图像数据 307200 bit, 分配的 RAM 原始容量 360 Kb。
若 PDS 按预期映射, 全片约 123.5/134 块, 余 10.5 块等效容量; 最终要检查层级报告, 不能用此估计代替综合。
不增加整幅 640x480/输入帧存储、PLL 或算法乘法器。输出端的 RAM/PLL 增量见 [video.md](video.md)。

## 时钟

流水线跑在输入的像素时钟下, 出口分别跨到输出扫描时钟和系统时钟:

- 小窗: 双时钟 RAM (`rtl/utils/dpram2c.v`), 后台在输入域写, 完整输入帧验证通过后切前台指针;
  指针和首次发布标志分别双触发器同步到输出扫描域。未发布时读口返回黑色。
  不把尺寸变化帧写进前台; 但换指针没有等输出场消隐, 小窗在切换处仍可能显示两份已验证帧的各一部分。
- NN: box4 的 RGB888 流经 8x24 异步 FIFO 跨到 50 MHz 系统域, 复用 NN 的输入 RAM 写口。
  只抓请求到达后的下一完整输入帧, 等 `crop.frame_commit` 验证和 FIFO 排空才自动推理;
  推理期间停止相机写入。坏帧结束请求并报错, 不运行半张图; 不新增整帧 RAM。
  握手、断流行为和 C 接口见 [nn.md](nn.md) 的“相机抓帧”。
- 复位: 系统复位在 `vision.v` 里同步到像素时钟。
- 约束: `mes50hp.fdc` 按 74.25 MHz (720p) 约束输入时钟, 并声明和系统时钟不相关。

## 输入分辨率

`crop` 按 SOF/EOL/valid 测量每行有效像素数及每帧有效行数, 不再用固定 `IN_W/IN_H`。
12 位计数支持至 4095, 溢出、半行或行宽不一致都作坏帧。连续两个完整帧尺寸相同且至少 640x480 后,
仅在 SOF 锁定 `(W-640)/2`、`(H-480)/2` (奇数差向下取整), 第三个帧开始尝试裁剪。
下游仍为 640x480 -> box4 -> 160x120, 与颜色算法的坐标约定一致。

高度变化可能发生在 ROI 全部送出之后, 因而裁剪输出只算后台数据:
下一 SOF 确认实际整帧尺寸与锁定尺寸相同、每行等宽、640x480 已完整裁出, 才提交颜色统计和小窗。
尺寸变化的帧、稳定等待帧、小于 640x480 的帧都不发布; 旧的已验证小窗和颜色结果保留。
不能仅凭电脑菜单的分辨率判断实际格式, 上板应读 `0x4000_5018`、`0x4000_501C`。

2026-10-21 的板上记录仍是: MacBook 设 800x600 时画面不正常, 设高一档能用, 红盒跟踪较稳。
本次只做仿真, 没有解决或重新归因该故障。仍保留的限制:

- EDID 首选 3840x2160@30 (297 MHz), 扩展还有 1080p/1440p, 超出输入时钟 74.25 MHz 约束。
  本次 **B2 跳过**: 未独立核实完整 EDID/CTA 描述符结构, 按任务约束保留原表及校验和,
  不提交未经验证的模式声明。主机可能仍选过高像素时钟, 上板须手动选受限模式;
  下一步要生成只含 <=74.25 MHz 模式的两块 EDID 并用解码器验证全部时序和校验和。
- DE 断开超过 4096 拍才算帧间消隐, 没接 VS (手册给出 W13, 极性未知)。
  800x600、1280x720 的测试源均满足行消隐 <4096、场消隐 >4096;
  其它模式即使有效宽高支持, 也可能不满足此边界判据, 不能据此宣称支持任意分辨率。
- MS7200 的补配置仍只在状态 0->2 时执行, 不返回写错、不重试。
  这些是 800x600 异常的排查线索, 不是本次证实的根因; 需要锁定状态、DE/PCLK/RGB 波形及芯片资料。

## 芯片

- MS7200: I2C 地址 0x56, 引脚 `pins.csv` 的 HDMI_RX_*, 寄存器表和 EDID 取自盘古例程 `06_hdmi_loop`。
  初始化在 `board_hdmi_init()`; 之后主循环里要隔一阵调 `board_hdmi_poll()`, 电脑接上或换分辨率时给芯片补设置。
- 和发送芯片 MS7210 共用一个复位脚, 所以复位在 `sw/bsp/board_hdmi.h` 里一起做。
- 数据位顺序按硬件手册表 3-6 (D[23:16] = R), 上板画面结构和颜色正确。
- EDID 扩展块第 3 字节改成 0xC0, 不声明 YCbCr; 否则 Mac 发 YCbCr, 当成 RGB 显示时蓝色发紫、肤色发黄。

## 算法试验

`model/` 里是 Python 试验脚本, 按硬件的方式算 (`box4` 缩到 160x120, 整数运算), 用 MediaPipe 手部 21 点当对照:

- `motion.py`: 帧差 -> 运动掩码 -> 重心, 实时看; `ablate.py`: 同一段视频跑各种组合打表。
- `color.py`: 颜色标记 (点选颜色, Cb/Cr 在容差内的点求重心)。

2026-10-21 的结论 (MacBook 摄像头, 人在电脑前挥手):

- 帧差找不准手: 脸、身体、摄像头晃动都算运动。最好的组合 (肤色 + 分格) 离手心中位数仍有 18 点 (160 宽), 跟踪门反而会锁在脸上。
- 颜色标记 (手拿红盒子) 顺光时稳定; 逆光时盒子亮面暗面断开, 重心会跳。
  红盒子 Cb=118 Cr=170 在常用肤色范围里, 但调好容差没有误识别到皮肤。
- MediaPipe 很准, 可以当老师: 以后要徒手, 用它给录的视频自动标注, 训练能放进 FPGA 的小 CNN。
  进行中, 见 [徒手手势模型](hand-model.md)。
